# Layer SwayFX and Bigscreen onto stock Bazzite

In November 2026 the supported way to build a custom Bazzite image is still Universal Blue's **ublue-os/image-template**. It has four parts: a Containerfile that starts `FROM` a published Bazzite image, a `build.sh` that adds packages with dnf5, a final `bootc container lint`, and a GitHub Actions workflow that rechunks, pushes to GHCR and cosign-signs the image every day. One repo can produce both of your variants after four edits: an `ARG BASE_IMAGE`, build args passed from the Justfile, a matrix in the workflow, and a per-image name. An `images.json` file is a clean way to feed that matrix, because each image's GPU base then becomes a one-line choice. The SwayFX laptop image has to sit on **`bazzite-nvidia:stable`**. It is the only Bazzite flavor that ships NVIDIA's 580 LTS driver, which is the only driver a Maxwell card can use. It keeps Plasma as a fallback session and adds **SwayFX 0.6.1 from Terra** plus Fedora's sway config as a second session. The Bigscreen TV image sits on **`bazzite-deck:stable`**. Fedora's **plasma-bigscreen 6.8.3** exactly matches Bazzite's KDE 6.8.3, and it becomes the desktop half of Gaming Mode once you patch a few Bazzite scripts that hard-code `plasma.desktop`. GitHub Actions plus GHCR is free for public repos and gives both machines normal `bootc upgrade`/uupd updates. A home-network registry is the best private alternative. GitLab's free tier cannot sustain daily rebuilds, and Codeberg's hosted CI cannot even pull the ~4.9 GB base image. Three live risks remain: Fedora shipping a newer Plasma than Bazzite's version lock allows, Bazzite someday dropping its LTS NVIDIA image, and a template ISO workflow that depends on an archived action and a config file that does not exist.

## The template needs four edits to build two images

The Bazzite docs offer three ways to make a custom image. The first is image-template, which they mark "recommended" over forking. The second is forking Bazzite itself. The third is BlueBuild, with the note that BlueBuild support must come from channels outside Universal Blue ([Bazzite docs](https://docs.bazzite.gg/Advanced/creating_custom_image/)). Both projects are active. image-template's last commit was **2026-11-07**, two days after a cosign bump ([commits](https://github.com/ublue-os/image-template/commits/main)). BlueBuild has a native one-recipe-per-image matrix ([BlueBuild](https://blue-build.org/how-to/multiple-images/)). Its ISO generator, though, still hard-codes JasonN3's build-container-installer, and that project is now **archived** ([BlueBuild ISO docs](https://blue-build.org/how-to/generate-iso/), [archived repo](https://github.com/JasonN3/build-container-installer)). Neither project builds multiple variants out of the box. So the choice comes down to support and tooling parity with Bazzite itself, and image-template wins on both.

The template is small. Its Containerfile has a `FROM scratch AS ctx` stage that holds `build_files` and `system_files`. The main stage is a hard-coded `FROM ghcr.io/ublue-os/bazzite:stable`, followed by one `RUN` that bind-mounts the context and runs `build.sh` with caches on `/var/cache` and `/var/log` and a tmpfs on `/tmp`. The file ends with `RUN bootc container lint` ([Containerfile](https://github.com/ublue-os/image-template/blob/main/Containerfile)). The Justfile has recipes for building, rechunking, tagging, disk images and VMs, but its `build` recipe creates an empty `BUILD_ARGS=()` array and never fills it ([Justfile](https://github.com/ublue-os/image-template/blob/main/Justfile)). The workflow runs on `ubuntu-26.04` on pushes, PRs, manual dispatch and a **daily 10:05 UTC cron**. It frees disk space, runs `just build` and then `just ostree-rechunk`, and pushes and signs only from the default branch ([build.yml](https://github.com/ublue-os/image-template/blob/main/.github/workflows/build.yml)). PRs therefore build without publishing, which makes them a free test run.

Turning that into a two-image factory takes four changes. You declare `ARG BASE_IMAGE` before the first `FROM`, make the Justfile fill `BUILD_ARGS`, turn the workflow into a matrix with `fail-fast: false`, and pass a per-leg image name to every `just` call. The OCI labels also need attention, because they read `image_name` from `image-template.env`. Driving the matrix from `images.json` keeps the variant layer independent of the GPU base. Each `variants/<name>.sh` script installs its desktop and never asks which GPU stack sits beneath it. If you later want an NVIDIA Bigscreen box, you add one row pointing at `bazzite-deck-nvidia`. A minimal version of the pattern looks like this:

```json
[
  {"name": "bazzite-swayfx",    "base": "ghcr.io/ublue-os/bazzite-nvidia:stable", "variant": "swayfx"},
  {"name": "bazzite-bigscreen", "base": "ghcr.io/ublue-os/bazzite-deck:stable",   "variant": "bigscreen"}
]
```

```dockerfile
ARG BASE_IMAGE=ghcr.io/ublue-os/bazzite:stable
FROM scratch AS ctx
COPY build_files /
COPY system_files /system_files

FROM ${BASE_IMAGE}
ARG VARIANT
ARG IMAGE_NAME
RUN --mount=type=bind,from=ctx,source=/,target=/ctx \
    --mount=type=cache,dst=/var/cache --mount=type=cache,dst=/var/log \
    --mount=type=tmpfs,dst=/tmp \
    /ctx/build.sh   # runs common.sh, copies system_files/{shared,$VARIANT}, then variants/$VARIANT.sh
RUN bootc container lint
```

In the workflow, a small setup job emits `jq -c . images.json` as a job output. The build job then uses `strategy.matrix.include: ${{ fromJSON(needs.setup.outputs.images) }}` and passes `matrix.base`, `matrix.variant` and `matrix.name` through to `just build`, the rechunk step, push and `cosign sign`. Each matrix leg runs on its own runner, so the two images never compete for the same 14 GB disk.

### Bazzite's build rules carry over into your image

A derived image inherits Bazzite's build discipline, and several of its rules are easy to trip over. Bazzite enables its COPRs and Terra while it builds, then its `finalize.sh` **disables** them all (Bazzite COPRs, Terra, fedora-multimedia, the akmods repo) in the shipped image ([finalize.sh](https://github.com/ublue-os/bazzite/blob/main/build_files/finalize.sh)). Your scripts therefore have to enable a repo for one transaction, for example with `--enablerepo=terra`. Bazzite also replaces Fedora's kernel with its `ogc` kernel and version-locks it ([03-install-kernel-akmods.sh](https://github.com/ublue-os/bazzite/blob/main/build_files/bazzite/03-install-kernel-akmods.sh)). Any extra kmod must match that exact kernel and Fedora release ([template README](https://github.com/ublue-os/image-template/blob/main/README.md)). Neither of your desktops needs one. Anything you put in `/var` behaves like a Docker `VOLUME` and is applied only at first install ([bootc filesystem](https://github.com/bootc-dev/bootc/blob/main/docs/src/bootc-filesystem.7.md)). Vendor configuration belongs in `/usr`, using drop-in directories.

Bazzite's `image-info.sh` writes `/usr/share/ublue-os/image-info.json` with `image-name`, `image-vendor`, `image-ref` and `base-image-name`, and rewrites `os-release` at the same time ([image-info.sh](https://github.com/ublue-os/bazzite/blob/main/build_files/image-info.sh)). A shared `common.sh` should rewrite the name, vendor and ref fields for each image. It should leave **`base-image-name: kinoite`** alone, because Bazzite's session and autologin helpers branch on that field and only know `kinoite` and `silverblue` ([os-session-select](https://github.com/ublue-os/bazzite/blob/main/system_files/deck/shared/usr/libexec/os-session-select)). Which helpers actually read `image-ref` is unverified.

### Signing only verifies anything if the image ships its own policy

The template ships no `cosign.pub`. You generate a key pair yourself, store the private key as the `SIGNING_SECRET` repo secret, and commit the public key ([README](https://github.com/ublue-os/image-template/blob/main/README.md)). The workflow signs with cosign v3.1.4 but forces the **legacy signature format** (`--new-bundle-format=false --use-signing-config=false`), because containers/image cannot yet read the new bundles. Bazzite signs with the same flags ([build.yml](https://github.com/ublue-os/image-template/blob/main/.github/workflows/build.yml)). The client side is where verification usually goes missing. Universal Blue's `policy.json` defaults to `reject` and requires signatures for `ghcr.io/ublue-os`. It sets **`insecureAcceptAnything` for every other registry namespace** ([policy.json](https://github.com/ublue-os/packages/blob/main/packages/ublue-os-signing/src/usr/etc/containers/policy.json)). Until your image carries its own entries, `ghcr.io/<you>/…` is pulled without any check. Bake three things into the image: `/etc/pki/containers/<you>.pub`, a `sigstoreSigned` entry for your namespace, and a `registries.d` file with `use-sigstore-attachments: true`. Without that last file, clients fail with "a signature was required, but no signature exists" ([Discourse](https://universal-blue.discourse.group/t/failed-to-invoke-method-openimage-a-signature-was-required-but-no-signature-exists/7335)).

For rechunking, keep the template's default `ostree-rechunk`, which runs `rpm-ostree compose build-chunked-oci` with 127 layers. Bazzite itself has moved to **chunkah**, which describes itself as the generalized successor to build-chunked-oci ([chunkah](https://github.com/coreos/chunkah)). The template's Justfile, however, warns that chunkah makes a complete copy of the image and can exhaust a runner's disk ([Justfile](https://github.com/ublue-os/image-template/blob/main/Justfile)).

## SwayFX goes on bazzite-nvidia because Maxwell rules out the alternatives

Measured on the laptop, the hardware decides the base image for you. The Precision 5510 pairs an Intel HD P530 (`i915`) with a Quadro M1000M, a 2 GB Maxwell GM107. The Intel device **owns every connector**: eDP-1, both HDMI ports and both DisplayPorts. The NVIDIA card exposes none, so it can only do PRIME render offload. NVIDIA's open kernel modules support only Turing and later GPUs ([NVIDIA](https://github.com/NVIDIA/open-gpu-kernel-modules)). That rules out every Bazzite image built on `nvidia-open`, including **`bazzite-deck-nvidia`**. Steam Gaming Mode is therefore not available for this laptop. The one usable image is `bazzite-nvidia`, which builds against **`nvidia-lts`** on an `ogc-lts` 6.18 kernel ([build.py](https://github.com/ublue-os/bazzite/blob/main/build.py)). The current stable release ships Nvidia LTS **580.196.07** on the 6.18.60 LTS kernel, alongside the 7.3.4 kernel used by the non-NVIDIA images ([release 45.20261117.1](https://github.com/ublue-os/bazzite/releases/tag/45.20261117.1)). The laptop's lifespan on Bazzite therefore depends on Universal Blue continuing to publish that LTS image.

SwayFX is **not in Fedora** ([mdapi](https://mdapi.fedoraproject.org/f45/pkg/swayfx)). It ships from two places. **Terra has 0.6.1**, the 2026-11-13 bugfix release on sway 1.12, wlroots 0.20 and scenefx 0.5 ([Terra](https://repos.fyralabs.com/terra45/), [releases](https://github.com/wlrfx/swayfx/releases)). The `swayfx/swayfx` COPR lags at 0.6 ([COPR](https://copr.fedorainfracloud.org/api_3/package/list?ownername=swayfx&projectname=swayfx)). Bazzite already configures Terra, so Terra is the better source. Both builds declare `Provides: sway = 1.12` and `Conflicts: sway`, with no `Obsoletes` ([COPR repodata](https://download.copr.fedorainfracloud.org/results/swayfx/swayfx/fedora-45-x86_64/repodata/)). Fedora's **`sway-config-fedora`** requires only `sway >= 1.8`, so it pairs with swayfx as long as both are installed in **one dnf transaction**. If they are not, dnf can pull in Fedora's real sway package. `sway-config-fedora` beats `swayfx-config-upstream` for an image because of its layered includes. Vendor snippets go in `/usr/share/sway/config.d`, admin overrides in `/etc/sway/config.d`, and user overrides in `~/.config/sway/config.d`, and a later file with the same name replaces an earlier one. Its `start-sway` wrapper also reads environment.d ([sway-config-fedora](https://gitlab.com/fedora/sigs/sway/sway-config-fedora)).

```bash
# build_files/variants/swayfx.sh
dnf5 -y install --enablerepo=terra swayfx sway-config-fedora sway-systemd \
    xdg-desktop-portal-wlr xdg-desktop-portal-gtk mako fuzzel grim slurp wl-clipboard \
    cliphist kanshi wlogout network-manager-applet blueman pavucontrol Thunar gvfs foot
echo 'SWAY_UNSUPPORTED_GPU=true' > /usr/lib/environment.d/90-sway-nvidia.conf
# effects and gaming defaults: /usr/share/sway/config.d/70-gaming.conf, 80-swayfx.conf
```

Keeping KDE as the fallback is not only a safety net. It is the low-risk architecture. Bazzite's desktop and Gaming Mode scripts assume Plasma or GNOME. `os-session-select` and `bazzite-autologin` map `kinoite` to `plasma.desktop`, and `08-install-steam-lutris.sh` installs a Plasma-specific resource booster ([08-install-steam-lutris.sh](https://github.com/ublue-os/bazzite/blob/main/build_files/bazzite/08-install-steam-lutris.sh)). Removing Plasma would mean patching every one of them, and the only proven removal precedent starts from `bazzite-gnome`, not KDE ([Smujb/bazzite-sway](https://github.com/Smujb/bazzite-sway)). There is no SwayFX-on-Bazzite prior art to copy. GitHub searches for SwayFX combined with Bazzite, BlueBuild or ublue returned nothing. Universal Blue removed its own sway images in 2025, and wayblue's sway image is still on Fedora 44 ([ublue-os/main](https://github.com/ublue-os/main), [wayblue](https://github.com/wayblueorg/wayblue)).

The extra session has four open integration points:

- **Login screen.** Since Fedora 44, KDE images log in through **Plasma Login Manager**, not SDDM ([Fedora change](https://fedoraproject.org/wiki/Changes/PlasmaLoginManager)). Whether PLM lists a third-party `sway.desktop` is unverified, so make it the first thing you check in a VM.
- **Portals.** Fedora's `sway-portals.conf` routes screencast and screenshots to `wlr`, everything else to `gtk`, and secrets to `gnome-keyring` ([sway-portals.conf](https://src.fedoraproject.org/rpms/sway/blob/rawhide/f/sway-portals.conf)). Install both portal backends explicitly.
- **Secrets.** Fedora 45's `pam_oo7` obsoletes `gnome-keyring-pam` ([mdapi f45](https://mdapi.fedoraproject.org/f45/pkg/)). Which secret service actually answers in the sway session is unresolved and needs testing.
- **Steam autostart.** Bazzite starts Steam from `/etc/skel` autostart ([12-finalize.sh](https://github.com/ublue-os/bazzite/blob/main/build_files/bazzite/12-finalize.sh)), and sway runs XDG autostart through `sway-xdg-autostart.target`, so Steam launches in SwayFX as well.

GPU behaviour under SwayFX follows from the display wiring. SwayFX renders on the Intel iGPU, but the `nvidia` module is still loaded. Sway 1.12 no longer refuses to start in that case, but it still shows a swaynag warning unless `SWAY_UNSUPPORTED_GPU=true` is set ([sway 1.12](https://github.com/swaywm/sway/releases/tag/1.12), [swayfx main.c](https://github.com/wlrfx/swayfx/blob/0.6.1/sway/main.c)). The variable only skips that check, so shipping it unconditionally keeps the variant script GPU-agnostic. SwayFX always uses scenefx's GLES renderer ([scenefx](https://github.com/wlrfx/scenefx)). Sway's Vulkan-only HDR10 path is therefore unavailable, a limitation tracked as issue #558. Animation-related crashes are among its open issues ([issues](https://github.com/wlrfx/swayfx/issues)), so keep `animation_duration_ms` modest. Games reach the M1000M through PRIME offload, either with `switcherooctl launch <cmd>` or the Steam launch option `__NV_PRIME_RENDER_OFFLOAD=1 __GLX_VENDOR_LIBRARY_NAME=nvidia %command%`.

## Bigscreen becomes Gaming Mode's desktop half on bazzite-deck

Plasma Bigscreen is in better shape than its history suggests. It was revived on Plasma 6, entered the Plasma release set as a new module in the **6.7 beta of 14 May 2026** ([KDE](https://kde.org/announcements/plasma/6/6.6.90/)), and reached **v6.8.3 on 2026-11-10** ([tags](https://invent.kde.org/api/v4/projects/plasma%2Fplasma-bigscreen/repository/tags)). It is Wayland-only. The old remote-controller daemon is archived, and a built-in inputhandler now handles HDMI-CEC remotes and SDL3 game controllers ([README](https://invent.kde.org/plasma/plasma-bigscreen/-/blob/v6.8.3/README.md)). Fedora ships `plasma-bigscreen` and `plasma-bigscreen-wayland` **6.8.3-1.fc45** as stable updates, so no COPR is needed ([Bodhi](https://bodhi.fedoraproject.org/updates/?packages=plasma-bigscreen)). Bazzite stable ships **KDE 6.8.3-1** from Fedora, an exact match ([release](https://github.com/ublue-os/bazzite/releases/tag/45.20261117.1)). The session file is `/usr/share/wayland-sessions/plasma-bigscreen-wayland.desktop` ([Fedora spec](https://src.fedoraproject.org/rpms/plasma-bigscreen/blob/rawhide/f/plasma-bigscreen.spec)). The research notes briefly disagreed here: Fedora's mdapi still showed Plasma 6.8.1, but Bodhi shows plasma-workspace 6.8.3 stable on Fedora 45 since 2026-11-15 ([Bodhi](https://bodhi.fedoraproject.org/updates/?packages=plasma-workspace)). Bodhi is the authoritative record.

That exact match won't last forever. Bazzite runs `dnf versionlock add "qt6-*"` and `"plasma-*"` on KDE images ([04-initialize.sh](https://github.com/ublue-os/bazzite/blob/main/build_files/bazzite/04-initialize.sh)). Meanwhile `plasma-bigscreen-wayland` requires `plasma-workspace-wayland >= %{version}`, and Fedora's updates repo normally keeps only the newest build. When Fedora pushes Plasma 6.8.4 before Bazzite rebuilds against it, a plain `dnf5 install plasma-bigscreen` will fail or try to fight the lock. The bifrost-htpc project has already been bitten by this kind of skew ([bifrost-htpc](https://github.com/inklikeurine/bifrost-htpc)). The defence is to install the Bigscreen version that matches the installed `plasma-workspace` and to fail the build on any mismatch. With a daily cron, a failure just means no new image that day. Clients keep booting the last good one, so the version gap shows up as a red CI run rather than a broken TV. Whether the version lock persists into derived images is unverified.

`bazzite-deck` is the right base because it already provides the two-mode machinery a TV box needs. It uses SDDM with `Relogin=true` and autologin into `gamescope-session-ogui-steam.desktop` ([holo.conf](https://github.com/ublue-os/bazzite/blob/main/system_files/deck/shared/usr/lib/sddm/sddm.conf.d/holo.conf)), plus `steamosctl` session switching and gamescope-session-plus ([deck 01](https://github.com/ublue-os/bazzite/blob/main/build_files/bazzite-deck/01-configure-desktop.sh)). Bigscreen only has to replace Plasma Desktop as the "desktop mode" target. SalongOS, an image-template derivative of `bazzite-deck`, does exactly that. It runs `steamosctl set-default-desktop-session plasma-bigscreen-wayland.desktop` and reports that Steam's "Switch to Desktop" then lands in Bigscreen ([SalongOS](https://github.com/MrCraigen/SalongOS)).

Bazzite hard-codes Plasma in three places, and all three need patching:

- `os-session-select` calls `steamosctl switch-to-desktop-mode plasma.desktop` on Kinoite bases ([os-session-select](https://github.com/ublue-os/bazzite/blob/main/system_files/deck/shared/usr/libexec/os-session-select)).
- `bazzite-autologin` falls back to `plasma.desktop` when desktop autologin is chosen ([bazzite-autologin](https://github.com/ublue-os/bazzite/blob/main/system_files/deck/shared/usr/libexec/bazzite-autologin)).
- The deck build writes `[session] desktop = "plasma.desktop"` into steamos-manager's `platform.toml` ([deck 04-finalize.sh](https://github.com/ublue-os/bazzite/blob/main/build_files/bazzite-deck/04-finalize.sh)).

Do not bake a `Session=` line into `/etc/sddm.conf.d`, because it would fight steamos-manager. Whether the patched `platform.toml` default alone is enough, without the per-user `steamosctl` call, is unverified. Keep a first-login `steamosctl set-default-desktop-session` as a backstop.

```bash
# build_files/variants/bigscreen.sh  (runs on bazzite-deck)
PV=$(rpm -q --qf '%{VERSION}' plasma-workspace)
dnf5 -y install "plasma-bigscreen-${PV}" "plasma-bigscreen-wayland-${PV}" plasma-keyboard  # plasma-keyboard name unverified
test "$(rpm -q --qf '%{VERSION}' plasma-bigscreen)" = "$PV"
sed -i 's/desktop_session="plasma.desktop"/desktop_session="plasma-bigscreen-wayland.desktop"/' /usr/libexec/os-session-select
grep -q plasma-bigscreen-wayland.desktop /usr/libexec/os-session-select    # fail loudly if Bazzite changes the script
sed -i 's|^Exec=/usr/bin/bazzite-steam %U$|Exec=steamosctl switch-to-game-mode|' /usr/share/applications/steam.desktop
rm -f /usr/share/applications/opengamepadui.desktop   # Bigscreen ignores NoDisplay/Hidden
```

The `grep` assertion after each `sed` matters. You are editing upstream scripts in place, and if Bazzite rewords one, the build should break in CI rather than the TV quietly landing in Plasma Desktop. Rewiring the Steam tile to `switch-to-game-mode` and removing the OpenGamepadUI entry both follow SalongOS ([build.sh](https://github.com/MrCraigen/SalongOS/blob/main/build_files/build.sh)).

Skipping Aura and Plank Player is sound, but it leaves one loose end. Bigscreen's envmanager sets **`BrowserApplication=aura-browser`**, so links have nowhere to open until you point that key at a browser the image actually ships. The envmanager also sets the on-screen keyboard to plasma-keyboard ([envmanager config.h](https://invent.kde.org/plasma/plasma-bigscreen/-/blob/v6.8.3/envmanager/config.h)), which the Fedora RPM does not require. That is why the snippet above adds it. A WirePlumber rule that prefers HDMI profiles is worth copying from bifrost-htpc ([wireplumber conf](https://github.com/inklikeurine/bifrost-htpc/blob/main/files/etc/wireplumber/wireplumber.conf.d/50-bifrost-tv-audio.conf)). On AMD, HDMI 2.1 FRL/VRR is behind a Bazzite Portal toggle and can flicker ([HTPC quirks](https://docs.bazzite.gg/Handheld_and_HTPC_edition/quirks/)).

The remaining gaps are upstream, not packaging:

- The on-screen keyboard cannot be driven by a TV remote alone ([#57](https://invent.kde.org/plasma/plasma-bigscreen/-/issues/57)).
- The system never auto-sleeps ([bko 524711](https://bugs.kde.org/show_bug.cgi?id=524711)).
- CEC volume never reaches an AV receiver ([bko 523726](https://bugs.kde.org/show_bug.cgi?id=523726)).
- There is no native Steam integration ([#45](https://invent.kde.org/plasma/plasma-bigscreen/-/issues/45)).

HDR in Bigscreen is whatever KWin provides. Content-driven HDR switching exists only in Gaming Mode ([auto-HDR recipe](https://github.com/ublue-os/bazzite/blob/main/system_files/desktop/shared/usr/share/ublue-os/just/98-bazzite-htpc-auto-hdr.just)). That division of labour is one more argument for sending games to Gaming Mode instead of running Steam inside Bigscreen. Running Steam inside Bigscreen also risks doubled controller input, because Steam Input's virtual pads and Bigscreen's SDL3 handler both react to the same controller. Since Bazzite's Steam autostart applies to every session, dropping that autostart on the Bigscreen image is a reasonable, untested hardening step.

## GitHub Actions wins on cost and a home registry wins on privacy

The path you chose, GitHub Actions plus GHCR, is the cheapest to keep running. Public-repo Linux runners have **4 vCPU, 16 GB RAM and a 14 GB SSD**, and private repos get half the CPU and RAM ([GitHub runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)). Public usage stays free after GitHub's 2026 pricing changes ([GitHub pricing](https://github.com/resources/insights/2026-pricing-changes-for-github-actions)). The base images are heavy: `bazzite:stable` is **4.45 GB** compressed and `bazzite-nvidia:stable` **4.90 GB**, each in 256 zstd layers ([GHCR manifest](https://ghcr.io/v2/ublue-os/bazzite/manifests/stable)). That is why the template frees runner space and keeps the lighter `ostree-rechunk`. The upstream template already builds `bazzite:stable` this way on hosted runners. Whether the NVIDIA base leaves comfortable headroom on 14 GB is unmeasured, and the first CI run will answer it. On the client side, uupd runs `bootc upgrade --check` and then upgrades. It skips updates below 20% battery, which matters for the laptop, and flags the system once the booted image is a month old ([uupd](https://github.com/ublue-os/uupd)). If you ever make the GHCR packages private, every client needs credentials in `/etc/ostree/auth.json`, because bootc ignores podman's auth paths ([bootc secrets](https://bootc.dev/bootc/building/bootc-secrets.7.html)).

Local builds are fully supported as well. `sudo just build` writes straight into root's containers-storage, and `sudo bootc switch --transport containers-storage localhost/<image>:latest` boots the result ([template README](https://github.com/ublue-os/image-template/blob/main/README.md)). Rebuilding the same tag and running `bootc upgrade` stages the new build. Community timers automate this, but one user collected about **100 GB** of stale images before adding `podman image prune` ([Discourse](https://universal-blue.discourse.group/t/locally-built-automatically-updating-custom-bootc-image/11706)). Getting the image to the second machine without a registry means copying an `oci` directory or `oci-archive` file and switching to it ([bootc offline](https://bootc.dev/bootc/bootc-registries-and-offline.7.html)). That box then sees an update only when someone replaces the file. Local transports also fall under the `insecureAcceptAnything` policy, so those deployments are unsigned in practice.

A home-network registry fixes the distribution problem. Run distribution or zot (zot conforms to the OCI distribution spec and supports cosign ([zot](https://zotregistry.dev/v2.1.23/general/concepts/))), mark it `insecure=true` in `/etc/containers/registries.conf.d` (bootc has no TLS-skip flag), and `bootc switch` to it once. From then on, `bootc upgrade` and uupd behave exactly as they do with GHCR. The catch in this setup is that the builder is the laptop. The TV would update only while the laptop is on and has rebuilt recently.

GitLab works but cannot keep up with daily builds. The Free tier gives **400 compute minutes a month**. The 50 GB medium runner costs two minutes per minute, while the small runner's 30 GB disk is tight for pull, build, rechunk and push ([GitLab minutes](https://docs.gitlab.com/ci/pipelines/compute_minutes/), [GitLab runners](https://docs.gitlab.com/ci/runners/hosted_runners/linux/)). Two images rebuilt daily come to about 60 builds a month against roughly 200 medium-runner minutes, so the budget fits weekly or manual builds at best. The registry itself is generous, since container images do not count toward Free storage quotas ([GitLab storage](https://docs.gitlab.com/user/storage_usage_quotas/)). Key-based cosign works there. Keyless GitLab OIDC signatures do not verify in containers/image, because the matcher cannot handle their SAN URIs ([upstream tracking](https://gitlab.com/dunn.dev/immutable/basef/-/issues/15)).

Codeberg's hosted runners are out of the question. They have a **10-minute maximum runtime** and only 2 GB of extra temporary storage, and Docker is unsupported ([Codeberg Actions](https://codeberg.org/actions/meta)). Codeberg's package quota is **1.5 GiB**, shared with LFS and releases, which is a third of one base image ([Codeberg storage](https://blog.codeberg.org/new-storage-limits-on-codeberg-what-you-need-to-know.html)). A self-hosted Forgejo instance with its own runner is technically possible. Its registry follows the OCI spec, but nobody documents cosign signatures on it, and Forgejo is absent from cosign's tested-registry list ([Forgejo](https://forgejo.org/docs/latest/user/packages/container/), [sigstore](https://docs.sigstore.dev/cosign/system_config/registry_support/)). Self-hosted GitHub runners are the realistic escape hatch if the 14 GB disk becomes a wall: they remain free for public repos, and GitHub has postponed its planned per-minute fee ([GitHub pricing](https://github.com/resources/insights/2026-pricing-changes-for-github-actions)). The trade is that you take on runner security and maintenance.

| Option | Cost | Client auto-updates | Signing | Verdict for two home machines |
|---|---|---|---|---|
| GitHub Actions + GHCR | Free (public repo) | Native uupd/`bootc upgrade` | Key-based cosign built in | **Chosen.** Lowest upkeep; public by default; 14 GB disk is the pinch point |
| Local build, containers-storage/oci-archive | Power only | Builder only; others need file copies | None in practice | Fast iteration loop, not a distribution method |
| Local build + LAN registry (distribution/zot) | Power only | Native while builder is up | Optional cosign + policy | Best private option; laptop-as-builder gates TV updates |
| GitLab CI + registry | 400 min/mo free | Native | Key-based only; keyless broken | Fits weekly builds, not daily |
| Codeberg / Forgejo | Free hosted, or self-run | Native if registry fits | Untested | Hosted: non-viable. Self-hosted: highest effort |
| Self-hosted GitHub runner | Free on public repos + hardware | Native | Same as GHCR | Fallback if hosted disk runs out |

## Virt-manager tests the packaging but not the GPU setup

Your planned test loop works, as long as it runs on the NixOS host rather than inside the Ubuntu distrobox. The host has podman 5.8.9, just, virt-manager and an active libvirtd. bootc-image-builder runs rootful and privileged, and it mounts root's `/var/lib/containers/storage` ([Justfile](https://github.com/ublue-os/image-template/blob/main/Justfile)). So build with `sudo just build <name> latest`, then run `just build-qcow2`. That produces a btrfs disk with a 20 GiB minimum size, which you import into virt-manager as an existing disk. The ISO path needs repair first. `just build-iso` and `build-disk.yml` both reference `disk_config/iso.toml`, which does not exist, and the shipped `iso-kde.toml` contains a `%post` that runs `bootc switch` to `ghcr.io/ublue-os/image-template:latest` ([iso-kde.toml](https://github.com/ublue-os/image-template/blob/main/disk_config/iso-kde.toml)). Create `iso-swayfx.toml` and `iso-bigscreen.toml`, each pointing at its own GHCR image.

A VM answers the integration questions:

- whether Plasma Login Manager lists `sway.desktop`;
- whether Steam's "Switch to Desktop" lands in Bigscreen;
- whether `image-info.json` and the signature policy are correct, which you can test by switching the VM to the GHCR tag with `--enforce-container-sigpolicy`.

It cannot reproduce the Intel/NVIDIA split, PRIME offload, CEC, HDMI audio or HDR, so those wait for real hardware. Two VM quirks are predictable. SwayFX's GLES-only renderer needs working 3D in the guest. The deck-based Bigscreen image boots straight into gamescope Gaming Mode, which a virtual GPU handles poorly. The documented way out of a stuck Gaming Mode session is `steamosctl switch-to-desktop-mode` from a TTY ([HTPC quirks](https://docs.bazzite.gg/Handheld_and_HTPC_edition/quirks/)).

For CI-built installers, the template's `build-disk.yml` still pins `osbuild/bootc-image-builder-action`, which is **archived**. Its README points users to `osbuild/image-builder-action` ([archived action](https://github.com/osbuild/bootc-image-builder-action), [replacement](https://github.com/osbuild/image-builder-action)). Bazzite itself builds live ISOs with Titanoboa, which requires `/usr/lib/bootc-image-builder/iso.yaml` inside the image ([Titanoboa](https://github.com/ublue-os/titanoboa)). With only two machines, you can skip custom ISOs altogether:

1. Install the official Bazzite ISO that matches each base: the NVIDIA KDE edition on the laptop and the Deck edition on the TV box.
2. Run `sudo bootc switch ghcr.io/<you>/<image>:latest` and reboot.
3. Switch once more with `--enforce-container-sigpolicy`, so that the image's own baked-in policy does the verifying ([bootc-switch](https://bootc.dev/bootc/man/bootc-switch.8.html)).

Both rebases stay inside the KDE family, which respects Bazzite's warning never to rebase between desktop environments ([rebase guide](https://docs.bazzite.gg/Installing_and_Managing_Software/Updates_Rollbacks_and_Rebasing/rebase_guide/)).

## Conclusion

Packaging is the easy part of this project. Each desktop is one dnf transaction from a repo Bazzite already trusts. The real work is in about half a dozen Bazzite scripts and files that assume the desktop is `plasma.desktop`: `os-session-select`, `bazzite-autologin`, `platform.toml`, `image-info.json`, the Steam desktop entry and the autostart. Your image is therefore a set of patches against a moving upstream. That is why the build should assert every patch and version match and fail loudly. A red daily build costs nothing, because bootc keeps clients on the last good image, while a silently mis-patched image costs a confused evening in front of the TV.

The `images.json` split pays off most on the laptop. All displays hang off the Intel iGPU, so the M1000M only ever does offload rendering. If Bazzite ever retires its LTS NVIDIA image, the fallback is to change the laptop's row to plain `bazzite:stable`. The SwayFX layer is untouched, and the only loss is a 2 GB Maxwell card for occasional game offload. The same design lets the Bigscreen image follow the TV hardware with a one-line base change if the box ever gets an NVIDIA card. The things to watch are upstream timing, not your code: Fedora's Plasma updates against Bazzite's version lock, Terra's SwayFX release cadence, and the template's eventual move away from its archived disk-image action.
